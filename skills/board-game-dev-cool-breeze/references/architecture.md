# Architecture

The server holds the only rules engine. The client renders the view it is sent and sends back an
action key. Everything else follows from keeping that boundary clean.

```
browser: transport -> session -> presenter -> components      (no rules code)
           ^  per-viewer snapshots          |  {"t":"act","key":"build:temple"}
           |                                v
server:  ws -> room actor -> engine (Legal, Apply, ViewFor) + bots -> store (seed + keys)
```

One accepted move: the actor checks the key is in the engine's current legal set, clones the state,
applies the engine's own action, writes the record durably, swaps the live state, then sends every
connection its own redacted view built by whitelist, with the next `choices`. Presentation events
travel beside the snapshot so the client can animate, but the snapshot alone is enough to resync.

Engine rules of thumb: standard library only plus an explicit allow-list; no clocks, files,
network, maps in rules logic or floats; all chance drawn from the seed at creation, in separate
streams per setup element; state as a value that clones by copy. View and wire types initialize
slices to empty (never null on the wire) and tag every field.

## Lessons

Each lesson is a rule and its reason. The label says how strong the evidence was: *seen once* (one concrete finding), *seen repeatedly* (recurring failures or independent checks across subsystems), or *owner decision* (an accepted preference, which a new owner may change).

- **2.01** Put the only rules engine on the server and keep the browser responsible for presentation and intent. This trades offline gameplay for a single legality implementation and a clear trust boundary. *(owner decision)*

- **2.02** Make local, bot and online modes use the same room and engine path. A mode should change seat control rather than introduce a second game implementation. *(seen repeatedly)*

- **2.03** Keep dependencies pointing inward: rules know nothing of sockets, files or clocks, and the room actor knows nothing of network transport. This makes the rules cheap to test and the actor reusable through different adapters. *(seen repeatedly)*

- **2.04** Use deterministic integer rules and stable ordered collections; isolate randomness behind a small tested generator. Clocks, unordered iteration, floating-point rules and hidden shared mutation make replay unreliable. *(seen repeatedly)*

- **2.05** Prefer state values that clone cheaply and have explicit bounded ownership. Fixed arrays and value structs worked well for bounded games, but the transferable requirement is predictable copying rather than a language-specific representation. *(seen repeatedly)*

- **2.06** Resolve finite shuffled randomness at creation and persist the seed with setup options and accepted actions. For games needing later chance, preserve the same replay guarantee by recording the random stream or outcomes explicitly. *(seen repeatedly)*

- **2.07** Give independent setup elements domain-separated random streams. An option that skips one draw should not silently change unrelated deals. *(seen once)*

- **2.08** Represent player intent with canonical, readable action keys generated by the engine. Validate exact membership in the current offered set and apply that engine-owned action, rather than reconstructing actions from client fields. *(seen repeatedly)*

- **2.09** Encode strategically meaningful alternatives in action identity while collapsing mechanically equivalent variants. An automatic cheapest payment is appropriate only when its recipient or allocation cannot change strategy. *(seen repeatedly)*

- **2.10** Send server-computed costs, explanations, previews and disabled reasons with the legal offer. Otherwise the thin client gradually acquires a second rules implementation through seemingly harmless display helpers. *(seen repeatedly)*

- **2.11** Start with complete per-viewer snapshots and separate structured events for presentation. Full snapshots simplify resync and recovery when payload measurements do not justify a diff protocol. *(seen repeatedly)*

- **2.12** Build each view, history and event stream by whitelist into a fresh output object. Removing secrets from a full internal object leaves every new field as a potential leak. *(seen repeatedly)*

- **2.13** Treat seeds, deal order, physical-copy identities, raw hidden action keys and observation fingerprints as sensitive. Hiding card faces alone does not stop these values from reconstructing private information. *(seen repeatedly)*

- **2.14** Serialize room mutations through one actor mailbox. Single-owner room state avoids a large web of locks and makes race and arrival-order tests tractable. *(seen repeatedly)*

- **2.15** For simultaneous games, validate every choice against one frozen decision point and resolve one canonical complete batch. Sequentially applying arrivals changes prices, knowledge and outcomes according to network timing. *(seen repeatedly)*

- **2.16** Persist private draft choices and confirmations without exposing their content or edit count to other seats. Public confirmation status and private revisions need separate semantics. *(seen repeatedly)*

- **2.17** Make acceptance transactional: clone, validate, write durably, then replace live state and publish. A storage failure must not reveal or acknowledge a transition that will disappear after restart. *(seen repeatedly)*

- **2.18** Store replay inputs and operational room metadata separately from derived engine state. Replay reconstructs game facts, while seats, permissions, pending work and idempotency barriers still need their own durable record. *(seen repeatedly)*

- **2.19** Version record syntax, game rules, wire protocol and bot policy independently. A cosmetic hash change, schema migration and strategic policy change have different compatibility consequences. *(seen repeatedly)*

- **2.20** Define which data is authoritative when a diagnostic hash disagrees with a legal replay. Refresh only under an explicit same-rules-version policy, and never treat a plain fingerprint as authenticated integrity. *(seen repeatedly)*

- **2.21** Dispatch stored files through a bounded validated header before game-specific decoding. Unknown schemas and game kinds must remain untouched rather than being misclassified as corrupt instances of an older game. *(seen repeatedly)*

- **2.22** Bound both serialized records and every path that rewrites them, including load-time refresh and archive operations. A file that the writer accepts but the reader rejects is a persistence bug. *(seen repeatedly)*

- **2.23** Use conditional first creation in one global room-code namespace, including archived records and successor rooms. Generating a code does not reserve it, so collision handling belongs at the durable write boundary. *(seen repeatedly)*

- **2.24** Share proven infrastructure between games while keeping rules, catalogs, actors and frame families separate where their semantics differ. Similar terminology is insufficient evidence that two engines should share behavior. *(seen repeatedly)*

- **2.25** Bound transport input, queues and slow-client output without blocking the actor. A latest-snapshot outbox is useful only if its event and history semantics still preserve everything the player needs to understand progress. *(seen repeatedly)*
